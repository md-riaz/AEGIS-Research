Introduction

  • Most dashboards are predefined and developer-dependent
  • Non-technical users know the insight they need but cannot translate it into SQL
  • Free-form LLM-generated SQL is flexible but unsafe for real systems
  • Average wait time for a new report: 3.2 days
  • 61% of reporting requests are recurring variations

Core Insight

User questions are limitless, but most reporting needs can be represented using a small set of reusable analytics primitives.

Think in LEGO blocks, not free-form clay. The system does not allow unlimited raw SQL — it supports controlled combinations of trusted reporting patterns.

Problem Statement

Unsafe & Unscalable

Raw SQL exposes sensitive data, is hard to cache, and unpredictable in performance.

Unpredictable & Unstructured

Free-form AI SQL may violate constraints, produce expensive queries, or ignore business definitions.

Ambiguous Questions

Users struggle to express intent without knowing the data model or SQL.

Lack of Persistence

Most systems focus on query generation or visualization, but not persistent reusable dashboard widgets.

▶ There is still no complete, safe, end-to-end workflow that converts natural-language business requests into reusable dashboard widgets.

Objectives

Design Objectives

  • Natural language interface for reporting
  • Predefined semantic layer of trusted business concepts
  • Ten analytics primitive taxonomy

System Objectives

  • Use existing LLM for structured intent extraction
  • Safe query compiler using approved templates
  • Chart/table/KPI outputs as reusable widgets

Evaluation Objectives

  • Evaluate correctness, safety, usefulness
  • 100-query benchmark over production schema

💡 The main contribution is not training a new AI model. The contribution is designing the system layers around an existing LLM so that natural-language reporting becomes safe and reusable.

What This Thesis Proposes

Core Idea

AI understands the question.
The system controls the execution.

  • LLM extracts structured intent (JSON), never SQL
  • Semantic layer maps business terms to schema
  • Template compiler generates safe SQL
  • Visualization selected by policy rules
  • Output persisted as refreshable widget

AI Freedom Boundary

AI CAN ✅

Rephrase intent • Infer missing context • Choose best metric • Decide chart type • Suggest follow-ups

AI CANNOT ❌

Invent joins • Bypass permissions • Hit raw tables • Create unbounded queries • Generate SQL directly

Freedom of thinking, not acting.

Formal Model

π = analysis plan • sql = compiled query • vis = chart spec • w = persisted widget

Safety: sql ∈ Q_safe(L, r) — all queries bounded by semantic layer L and role r.

Five Design Principles

  • Interpret and execute separately
  • Make business semantics explicit
  • Bound the executable space
  • Guide visualization by policy
  • Persist outputs as artifacts

Why Perfect?

The LLM is constrained to structured JSON output with a strict schema and bounded vocabulary. Intent classification is a well-bounded task that modern LLMs handle reliably when properly prompted.

The hard problems (semantic mapping, SQL safety) are handled by deterministic system components, not the model.

Safety Analysis: Why 0% Unsafe?

Structural Safety Guarantee

SafeDash achieves 0% unsafe SQL by design, not by chance:

  • No SQL generation by LLM — model produces JSON intent only
  • Template-only compilation — SQL from allow-listed patterns
  • Closed vocabulary — all identifiers from semantic layer
  • AST validation — rejects forbidden constructs
  • No string interpolation — SQL injection structurally impossible

Proposition 1: No query in Q_safe(L,r) can reference a table, column, or row not enumerated in L for role r.

Baseline Unsafe Queries (7/99)

  • INSERT/UPDATE/DELETE statements
  • UNION clauses exposing other tables
  • Subqueries against system tables
  • Unbounded JOINs (no LIMIT)
  • References to unauthorized columns

Conclusion & Future Work

Key Contributions

  • 10-class intent taxonomy from 312 real requests
  • Governed pipeline: LLM interprets, system executes
  • 0% unsafe SQL vs. 7.1% baseline
  • 64.7% semantic correctness vs. 0% baseline
  • 100% execution validity
  • Widget persistence for dashboard reuse

Safety properties that must hold unconditionally should be enforced by structure, not by probability.

Future Extensions

  • Multi-turn conversational context
  • Retrieval-augmented generation (RAG)
  • Voice controls for eyes-free analysis
  • Automated alerts when metrics drop
  • Semi-automated semantic layer extension
  • Cross-domain portability evaluation

Expressiveness

97.4% of real requests covered. The 2.6% gap represents complex cohort queries outside current templates — addressable by template extension.
